# 解析ノートの相違点の判定と検証方針

作成日：2026-10-04

解析の初期に作った2つのノート（以下 **Claude**・**ChatGPT**。元ファイルは 2026-10-06 に削除）で食い違っていた点を、
`inspection.md` の調査結果を正として判定する。判定できないものは、実装方針を2つ以上用意し、
実セーブで正しく編集できたほうを採用する。

- §1：判定できていない項目（U-n）
- §2：判定できた相違（D-n）
- §3：判明した U 項目。番号はコードのコメント・テストから参照しているので変えない

採用した内容は `save_format/`（[README](save_format/README.md) と各 chunk）に反映してある。

## 0. 前提

### 0.1 inspection.md の調査結果

| # | 内容 |
|---|---|
| I-1 | 主人公名は31文字まで |
| I-2 | 武器レコード長は0xA0 |
| I-3 | 実装されている範囲では、tarotshogun（WayOfTheSamurai4SaveEditor、V1.06 Take 2）の実装は正しい |

### 0.2 I-3 の適用範囲

ChatGPT のノートは tarotshogun のソースを根拠にしているため、I-3 が及ぶ項目では ChatGPT 側を採用する。
ただし、次の項目は「実装されている範囲」に含めない。

- 作者自身が誤りや未完成と注記しているもの：俺流名の位置（0x19210）、流通数（+0x99）の解釈、正道刀の鍔の定義値
- tarotshogun が読み書きしていないもの：流派、開始地点、ストーリー、特典、流通中の刀など
- tarotshogun に定義がないID（未登録パーツなど）
- ChatGPT が独自に立てた推測：2バイト×4値の仮説、未登録パーツの推定ID
- tarotshogun の完成武器ID の表のうち、31（天井割）と 94 以降：🟢 と食い違い、サンプルのセーブ（完成武器ID 110＝陸奥守吉行）も 🟢 側と合う。
  正しい ID は `save_format/datatable/weapon/complete.csv`

### 0.3 「正しく編集できた」の判定基準（2案以上ある項目に共通）

1. `sample/` のコピーに対して、案A／案Bのそれぞれで同じ編集を行う（元ファイルは触らない）
2. ゲームを完全に終了した状態から起動してロードする（Steam Cloud はオフ）
3. 次をすべて満たした案を「正しい」とする
   - ロードでき、フリーズ・クラッシュしない
   - ゲーム内の表示が意図した値になっている
   - そのままゲーム内でセーブし直したファイルを読むと、編集した値が保たれている
   - 編集したフィールド以外のバイトが、ゲームの再セーブで想定外に変わっていない（再セーブ前後の差分で確認）
4. 両方とも満たした場合は、案の差が出る別の入力で追加テストする。両方とも失敗した場合は、その項目を読み取り専用のままにする

## 1. 判定できない項目と実装方針

<a id="u-1"></a>
### U-1 レイアウトを固定オフセットで扱えるか

- **論点**：tarotshogun は固定オフセットで、構造体のサイズ（0x48BB0）分だけ読み書きする。
  一方、Wiki には「進行状況やDLCで位置がずれる」とある。I-3 は V1.06 Take 2 の、
  tarotshogun が想定したセーブでの正しさしか保証しない。
- **案A（固定オフセット）**：[まとまりの一覧](save_format/README.md#3-まとまりの一覧)と[武器レコード](save_format/chunks/weapon-record/README.md)のオフセットをそのまま使う。ファイルサイズが 0x48BB0 と一致したときだけ編集を許可する。
- **案B（アンカー探索）**：武器はレコード長 0xA0 の周期で妥当な値のレコードが続く場所、アイテムは8 B周期で既知ID＋個数≤999の場所、
  名前はUTF-16文字列を探す。見つかった位置が案Aと違う場合は案Bの位置を使う。
- **確認方法**：条件の違うセーブ（DLCあり／なし、序盤／終盤、周回数違い）を `sample/` に集め、
  ファイルサイズと案Aの位置での値の妥当性を調べる。全サンプルでサイズが同じで、案Aの位置が妥当なら案Aを採用する。
  1件でもずれたら案Bを採用する。
- **採用までの扱い**：案Aの位置で妥当性検証に通った領域だけを編集可能にする（AGENTS.md の規則どおり）。

<a id="u-4"></a>
### U-4 HP・活力（0x35A4〜0x35B0）の意味

- **論点**：tarotshogun は 0x35A4＝活力、0x35A8＝HP の1つずつしか持たない。PS3版では 0x35A4〜0x35B0 が命（現在／最大）・活力（現在／最大）の並び。
- **判明していること**（[vitals](save_format/chunks/vitals/README.md)）：0x35A8＝最大HP、0x35AC＝活力の現在値、0x35B0＝活力の最大値（[U] 2026-10-04・05）。
  活力の現在値は時間で減る（約1分で 10）。ただし峰打に切り替えただけのセーブでは、プレイ時間が +298 秒でも減らなかった
- **残る論点**：
  - 0x35A4 の意味。[TS] は「活力」とするが、活力は 0x35AC／0x35B0 にあるので矛盾する。PS3版の並びでは現在HP（🔶）
  - 活力が何によって減るのか
- **次の確認方法**：
  - 0x35A4 に最大HPより小さい値を書いてロードし、HPゲージが変わるか見る
  - 0x35AC に 500 などの別の値を書き、ロード直後（操作前）の表示を見る
- **採用までの扱い**：エディタは最大HP（0x35A8）と活力の最大値（0x35B0）だけを扱う。0x35A4・0x35AC は表示も編集もしない（ユーザー判断、2026-10-04）。

<a id="u-6"></a>
### U-6 俺流名の位置と構造

- **論点**：Wiki では 0x19200付近（✅）。tarotshogun は 0x19210 から80 B×64件（8 Bヘッダ＋64 B名前＋8 Bフッタ）だが、作者自身が位置不正と注記しているため I-3 の対象外。
- **案A**：0x19210 からの80 B×64件として読む（tarotshogun の仮定義）
- **案B**：0x19200付近でUTF-16文字列をアンカー探索し、見つかった位置を名前の先頭とする
- **確認方法**：既知の俺流名があるセーブで、各案の位置に名前があるかを読み取りで確認する。
  次に、名前を1文字だけ変えて書き込み、ゲーム内の流派一覧の表示を見る。
- **採用までの扱い**：読み取り専用。

<a id="u-11"></a>
### U-11 流通中の刀の1件あたりの長さ

- **論点**：ユーザーの実データで 0x440D0 から始まることを確認済み（✅）。1件のバイト数は❓。
  I-2 で武器レコードが0xA0と分かったので、同じ長さである可能性が高くなった。tarotshogun ではこの領域は Padding。
- **案A**：0xA0（武器レコードと同じ構造）
- **案B**：別の長さ。0x440D0 以降で繰り返しの周期を探して決める
- **確認方法**：0x440D0 から0xA0刻みで読み、[武器レコード](save_format/chunks/weapon-record/README.md)の位置（攻撃力・魅力・名前）に妥当な値が並ぶかを確認する。
  並べば案A。並ばなければ自己相関で周期を求める（案B）。
- **手がかり（2026-10-05、`sample/S4-DATA_00`）**：空き武器レコード（+0x06〜+0x65）と同じバイト列が `0x440D2` から **0xA4 刻み**で15件見つかった。
  0xA0 のレコード＋4 B の可能性がある（🔶、中身のある件では未確認。[market-weapons](save_format/chunks/market-weapons/README.md)）。
- **採用までの扱い**：読み取り専用。

<a id="u-12"></a>
### U-12 チップ・木札のアイテムID

- **論点**：PS3版では 0x2D＝チップ、0x2E＝木札。tarotshogun には定義がない。
  PS3版ではこのIDを書き込むとセーブ画面でフリーズしたという報告がある。
- **案A**：0x2D／0x2E を PS3 と同じ意味で扱う
- **案B**：PC版では別のIDを使う。チップ・木札を所持したセーブで、アイテム領域を検索して決める
- **確認方法**：チップ・木札を手に入れる前と後のセーブを比較する（読み取りだけで決着できる）。
- **観察（[U] 2026-10-04）**：Steam版で 0x2D／0x2E を書き込むと、フリーズはしなかったが、ゲーム内でセーブできなくなった。
- **採用までの扱い**：選択肢に出さない（ユーザー判断、2026-10-04）。既にこの ID が入っている枠は、ほかの ID への変更だけを許す（ユーザー判断、2026-10-04）。

## 3. 判明した U 項目

<a id="u-2"></a>
- **U-2 銘「人斬り」のバイト列**：`6A 01 00`（案A。他の19種と同じ `<ID下位> 01 <番号>` の規則）。不採用：[TS] の定義値 `0x016A00`（`00 6A 01`、案B）。
  根拠：銘なしの武器に各案を書いてロードすると、案A は「人斬り」、案B は「……」と表示された（[U] 2026-10-05）。エディタは案B のバイト列を未知の銘として扱う
<a id="u-3"></a>
- **U-3 パーツ領域（+0x08〜+0x0F）の区切り方**：2 B×4（刃 ID、X＝鞘 ID、鍔 ID、柄 ID。各 u16）。書き込みはすべてこの形で、刃は ID と X、鍔・柄は ID だけを書く（ユーザー判断で決着 2026-10-06）。
  不採用：[TS] 準拠の3バイト値（案A）。[TS] の3バイト値のまま書くと X の上位バイト（+0x0B）が前の武器のまま残る（和泉守兼定の上に柾重を書くと X 0x1CD で「表にない鞘」と出た。[U] 2026-10-05）。
  既知パーツを揃えて書いたバイト列は [TS] の3バイト値（I-3）と同じ。読むときの照合は [TS] の3バイト値のまま。
  刃ごとの X は `save_format/datatable/weapon/blade.csv` の `sheath_x`。規則で X を計算した [CT] の刃 23 本はゲーム内で未確認だが、値は 🟢
<a id="u-5"></a>
- **U-5 武器名の最大文字数**：17文字まで（案A。[TS] 作者の注記「ゲーム内では17文字まで」）。不採用：31文字（案B）。
  根拠：ユーザー判断（[U] 2026-10-05）。エディタは17文字を超える武器名を拒否する
<a id="u-7"></a>
- **U-7 開始地点（0x13）の型**：0x13 の u8（案A）。不採用：0x12〜0x13 の u16 LE（案B）。
  根拠：0x13 の1バイトだけを書き換えたセーブで、出現場所に反映されることをユーザーが確認した（[U] 2026-10-04）。クラッシュ値（00, 13, 24, 28, 29, 2C〜C4）は選択肢に出さない
<a id="u-8"></a>

<a id="u-9"></a>

<a id="u-14"></a>
- **U-14 謎の鍵・拷問部屋の鍵のアイテムID**：拷問部屋の鍵＝`0xED`（237）、謎の鍵＝`0xEE`（238）🟢（2026-10-07）。会談の手紙は `0x00`（[U] 2026-10-05）。
